# M0 架构总结与后续开发准则

核对日期：2026-09-30。供开发者和后续 AI 在修改聊天、账户数据、Windows 桌面窗口前阅读。逐脚本的改动原因和面试问答见 [M0 修改报告](M0_IMPLEMENTATION_REPORT_2026-09-30.md)。

## 完成范围与来源

M0 的代码基线来自 Git `8473655` 的快照、回合制队列、场景接线与相关文档；本次开始前用户另有未提交的 `ChatReplyResult.cs`、`AIChat.cs`、`SearchDecisionService.cs`、`ConversationService.cs` 终态改动。本轮补齐数据库迁移/级联、应用日志与配置、前台感知隔离、队列气泡时序和测试。不能把 Git 已提交改动、本次开始前工作区改动和本轮新代码混为一次提交。

## 必须保持的运行不变量

| 领域 | 规则 | 回归方式 |
| --- | --- | --- |
| 身份 | 异步入口捕获 `SessionSnapshot`；用 UserId、CharacterId、SessionVersion 判定仍有效，不以可改名的 Name 判定身份。 | 在搜索、请求、主动气泡期间切角色、退出、重登，旧结果不得进新角色。 |
| 轮次 | 一次输入一个 `ChatTurn`/`TurnId`；同一会话串行；轮到执行才保存用户消息。 | 连续发送 A/B，历史顺序应为 A 用户、A 终态、B 用户、B 终态。 |
| 请求体 | `UserMessageId` 排除已落库的当前消息，再追加当前输入一次。 | 捕获发给模型的 messages，当前输入恰好一条。 |
| 终态 | Success、Failure、Cancelled 分流；失败/取消不能写 Assistant 正常回复或增加成功关系值；请求和锁必须释放。 | 超时、HTTP、断网、坏 JSON、空回复、主动取消后继续发送下一轮。 |
| UI | 待执行气泡由 TurnId 暂存；未落库时取消/失败就移除；切会话清空并按新角色加载历史。 | 排队 B 后切角色，B 气泡消失；旧角色已落库的 A 留在旧历史。 |
| 数据 | 所有权以稳定 UserId/CharacterId 表达；改名保持关联；用户/角色删除事务清理所有关联表；当前角色先切换再删除。旧库无法认领的角色保留原记录和关联数据，以 `LegacyUnclaimedCharacter` 标记，不能登录、展示或编辑。 | 合成旧库迁移、隔离、改名、级联和故障触发器回滚。 |
| 平台 | Presentation 不直接 P/Invoke/持有 HWND；窗口和前台感知经 Platform，原生插件只给 Windows x64。 | Unity Editor 编译及 Windows x64 Player 自检、透明、点击穿透、多显示器/DPI。 |
| 配置日志 | 真实密钥只在本地 config.json；应用级日志只订阅一次，记录指纹、不写原文；缺 Prompt 阻断启动。 | 缺配置/缺 Prompt 的可定位错误，UI 重建不重复日志。 |

## 未来修改这部分代码的准则

1. 修改入口参数时先画出请求创建、暂停、恢复、提交、取消的路径。凡跨 `yield` 的用户/角色/标题/进程等参数都用捕获值；提交前用 `IsCurrent`。
2. 只有 `ConversationService` 决定普通聊天 Turn 的执行顺序和终态；UI 不直接写消息、调用模型或修改关系。新增异步阶段必须在阶段前后都处理会话失效。
3. 新的失败原因加入结果协议，不能把异常文字冒充 Assistant 回复。若加入重试，保留 TurnId 并防止重复保存用户输入/Assistant 回复。
4. 扩充数据库表时先定义归属 ID 与事务边界，再设计版本迁移、备份和副本测试。角色资料中的 `UserName` 是兼容展示字段，不得重新作为权限或所有权依据。隔离角色仍在原表且可能没有 `UserId`；所有角色查询必须排除它，尤其不能让不存在的用户名通过空 `UserId` 匹配它。
5. 删除路径须明确关联表、当前会话保护及失败回滚。UI 只在事务成功后刷新；不要在事务中途触发会话或 UI 事件。
6. 新增 Windows 功能时先扩展 Platform 服务和模型；Win32 ABI 留在 Native。要核对 DLL 导入平台、API 版本/能力检测与失败降级，不用 `Screen.currentResolution` 估工作区。
7. 新日志只记录无敏感信息的结构化状态；不要记录原始聊天、Prompt、API 密钥、前台窗口标题或完整网络返回。订阅与应用寿命绑定。
8. 保留 `.meta` GUID；不直接编辑 `Library`、`obj`、生成 csproj 或真实运行数据库。Player 验证使用隔离工作区并记录 Unity 版本、构建目标、环境、结果。

## 已知风险与用户决定

- 固定默认管理员密码 `123456` 且登录页预填：用户选择本次保持现状，列入后续安全阶段；公开发布前应修复。
- 现有旧库确有 1 个找不到当前用户的角色，关联 1 条关系和 2 条事件；其历史 UserId 也不在用户表内。原先“遇孤儿阻断整个应用”使正常账号无法登录；用户随后同意改为隔离孤儿并继续迁移。`LegacyUnclaimedCharacter` 保存角色 ID 标记，原角色及其关联记录留在原表；全局角色查询只返回与现存用户关联的角色。禁止把孤儿自动挂到管理员或删除原始数据。实际旧库尚未运行新迁移。
- 旧库增列后的物理 `UserId` 可空，应用层校验/仓储写入保证非空；若将来允许外部 SQL 写入，应重建表增加数据库约束。
- 不具备真实 API 密钥的隔离验证只能证明错误路径，无法证明联网聊天服务端行为。Windows Player 与多显示器实际体验必须单独记录。
