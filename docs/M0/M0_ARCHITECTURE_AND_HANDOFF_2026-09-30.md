## 后续修改准则

1. 跨 yield 的身份、标题、进程、输入均用捕获值；新阶段前后和提交前检查 IsCurrent。不要用同步兼容重载重新捕获身份。
2. 普通聊天顺序和终态由 ConversationService 决定；UI 不直发模型或写聊天。重试先定义 TurnId/消息 ID 是否复用以及幂等性。
3. HTTP 成功、业务解析成功、数据保存成功、关系更新成功、UI 通知是不同提交点；不要用错误文本冒充正常回复，定义 E04 的失败语义后再改。
4. 新表/数据修复先定义稳定 ID、版本与事务、备份和副本测试。隔离角色留在原表；无效用户名必须返回空，避免 null ID 查询命中。情绪名称键是现有违例，不能仿照。
5. 级联删除事务成功后刷新 UI；认领隔离数据要可信归属证据、完整关联检查与专门事务，无自动猜测/清理。
6. Win32 留 Native，业务只扩平台接口和普通值类型。logical size 与 physical bounds 分清，服务 bool/Try 失败不可当成功。
7. 日志按 2026-10-04 用户决定恢复可读原文与错误堆栈，位置为项目根目录/Player exe 旁的 run_log.txt；保留应用级唯一订阅。不要打印真实密钥；Unity 日志、事件库和网络 payload 分别核对。
8. 保留 .meta GUID，不编辑主工程 Library/obj/生成 csproj；验证记录环境/版本/日期。本次文档更新不产生新 Unity 测试证据。
9. 世界寿命独立于会话，先做进入/退出/失败恢复，再扩资源框架；现有窗口服务常驻不代表所有 Manager 应常驻。详见实现指南。
10. SakuramachiSceneLoop 独占列车/杆/灯，欢迎只写角色/镜头；现有音轨/材质不能按旧资料重建覆盖。
